# PC Guard 3.2: текущее состояние системной защиты

Собственный драйвер протокола 4 собран для x64. Не подписан, не установлен и не испытан в ядре. Наличие SYS не считается активной защитой. На основной Windows IObit, Defender, другие драйверы, Secure Boot и Test Signing не переключались.

В код добавлены двухфазные prepare/commit/abort с сохранением прежней политики; снимок существующих файлов и NTFS-потоков с удерживаемыми дескрипторами; проверка старых writable mappings через MmDoesFileHaveUserWritableReferences; каталог VolumeSerial/FileId128; контексты потоков; инвалидация хеша при записи; ранняя проверка хеша при открытии файла. Callback создания секции только инвалидирует кеш и не использует недокументированный ACCESS_DENIED. Есть ограничения hardlink, переноса данных из выбранных папок и изменения родителей. Сбой подготовки не должен заменять старую политику.

Пользовательская подготовка каталога проверена искусственными DAT/ADS-файлами: удержание против записи и rename, отказ при старом пишущем дескрипторе, возврат доступа после Dispose. Разбор протокола проверяется C-стендом с guard page и 100000 случайных входов. Это не проверка работы callbacks в ядре и не доказательство отсутствия гонок/обходов/BSOD.

Нужны: отдельная Windows с подходящим гипервизором/vTPM, kernel regression из driver/SIGNING.md, Driver Verifier, совместимость NTFS/ReFS и антивирусов, HLK/подпись, финальные INF/CAT и согласование системного Driver Store с ограничением D. Файлы подготовки среды находятся D:\Codex\work\PCGuard-lab. Windows-гость ещё не установлен.

Защита ограничена выбранными папками и точными хешами; это не общий поведенческий анализ ransomware, не ELAM, не глобальный контроль скриптов или памяти. Классические приложения камеры всё ещё требуют отдельного перехвата и физических испытаний; текущие пользовательские запреты касаются ограниченного списка AppContainer/UWP.

База остаётся 19788 SHA-256, из них 19216 исторических malware-хешей и 572 campaign IOC только предупреждают. Чтение TXT новым нативным процессом ранее получало отказ; причина не подтверждена. Архивы и память не сканируются. См. rules/manifest.json, README.txt и VERIFICATION.json.

Прямой запрет отображений через AcquireForSectionSynchronization не реализован: контракт WDK допускает отказ SyncTypeCreateSection только при недостатке ресурсов. Старые отображения проверяются на commit, но передача разрешённого пишущего handle и обход через старые читающие handle требуют отдельного решения. Это остаётся блокером полноценной защиты, а не скрытое заявленное покрытие.
